📘 How this was built

System prompt design

The underlying Claude call is scoped narrowly to one job: convert a learner's inputs (skill, level, hours/week, deadline, goal) into a structured JSON roadmap — nothing else. The prompt instructs Claude to:

  • Return ONLY raw JSON matching a fixed schema (no prose, no markdown fences) so the frontend can render it directly into the dashboard.
  • Break the plan into 3–6 sequential phases, each with a name, duration, goal, milestone label, and 3–6 checkable tasks.
  • Include a short resources array (course/book/tool suggestions with a one-line "why").
  • Handle edge cases explicitly: if the skill field is empty, nonsensical, or clearly abusive/unsafe, Claude returns a JSON error object instead of inventing a plan, which the UI renders as the error state.
  • Keep tone playful and encouraging in the phase goals and milestone labels (matching the gamified UI) without becoming childish or padding real content with filler.

Why the UI fits this use case

A roadmap builder isn't a chat — it's a plan you want to glance at and act on. So instead of a chat bubble, the output renders as a dashboard: a top-level XP progress bar (percentage of tasks checked), a vertical phase timeline with connecting line and dot markers (borrowed from quest/level-up game UIs, since the brief asked for playful/gamified), and a resources grid. Checkboxes are real, persistent-in-session state — checking tasks visibly fills the progress bar and flips phase dots from violet (in progress) to lime (done), giving the "leveling up" feedback loop the tone called for.

Extending this assistant

  • Tools: connect a calendar MCP so generated phases can be pushed as real calendar blocks based on hours/week.
  • Memory: persist the generated plan and checkbox state (e.g. via window.storage) so a returning learner sees their in-progress roadmap instead of a blank form.
  • Multi-step flow: add a follow-up call that regenerates remaining phases when a user reports falling behind or finishing early, keeping the plan adaptive rather than static.
  • Verification: add a lightweight quiz-generation call per phase to test the learner before marking a milestone complete, rather than trusting self-reported checkboxes.
