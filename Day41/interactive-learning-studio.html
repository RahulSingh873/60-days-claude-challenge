Module 01 / 04

Foundations — Objects, this & the Prototype Chain

The mechanism underneath every JS object, before any syntax sugar is added.

Explanation

Every JavaScript object carries a hidden internal link — commonly called [[Prototype]] and accessible via Object.getPrototypeOf(obj) or the legacy __proto__ — pointing to another object. When you read a property that doesn't exist directly on an object, JS doesn't fail immediately. It follows that link to the linked object, checks there, and keeps following the chain until it either finds the property or reaches an object whose prototype is null.

This is fundamentally different from classical inheritance in Java or C++, where a class is a static blueprint that gets copied at compile time. In JavaScript, the chain is live: objects are linked, not copied, and the lookup happens at runtime, every single time.

Analogy

The office memo chain — imagine you ask a junior employee (your object) a question. If they don't know the answer, they don't guess: they forward it to their manager (the prototype). If the manager doesn't know either, it goes up to the department head, then the VP, and so on — until someone answers or you reach the CEO's empty inbox (null), and get undefined back.

Example

const animal = { eats: true };
const rabbit = { jumps: true };

// link rabbit's prototype to animal
Object.setPrototypeOf(rabbit, animal);

console.log(rabbit.jumps); // true — own property
console.log(rabbit.eats);  // true — found via prototype chain
console.log(rabbit.flies); // undefined — chain exhausted at null

Nothing was copied. rabbit still only owns jumps; eats is resolved live through the link every time you ask for it.

Diagram — Property Lookup

Comparison

Classical (Java/C++)

Classes are fixed blueprints. Inheritance is resolved at compile time and can't change once an object exists.

Prototypal (JavaScript)

Objects link directly to other objects. The chain can be reshaped at runtime with Object.setPrototypeOf.

Common Misconceptions

Myth"__proto__ and .prototype are the same thing." They're not — .prototype is a property that exists only on functions, used as the template for objects it constructs. __proto__ is the actual link every object has to its prototype.
Myth"Prototype chain lookups copy properties down." They don't copy anything; they read live, so a change to animal.eats is instantly visible to every object below it in the chain.

Key Takeaways

  • Every object has an internal link to a prototype object, forming a chain.
  • Property lookups walk the chain until found or until null is reached.
  • The chain links objects live — nothing is copied.
  • hasOwnProperty() distinguishes an object's own properties from inherited ones.

Module 02 / 04

Constructor Functions & .prototype

Complete Module 1's quiz to unlock this module.

🔒 Locked — finish the Module 1 quiz above.

Explanation

Before class existed, JS developers built reusable object "types" with ordinary functions, called with new. When a function is invoked with new, JavaScript creates a brand-new object, sets its prototype to the function's .prototype property, binds this to that new object inside the function, and returns it automatically.

Methods defined on Function.prototype are shared by every instance through the chain, rather than duplicated into each object — this is the real reason prototypes exist: memory-efficient shared behavior.

Analogy

A cookie cutter — the constructor function is the cutter, new presses it into dough to create a new cookie (instance) with its own filling (own properties), but every cookie made from the same cutter shares one recipe card pinned to the wall (.prototype) for its shared behavior.

Example

function Dog(name) {
  this.name = name; // own property, per instance
}

Dog.prototype.bark = function() {
  return `${this.name} says woof!`;
}; // shared method, lives once on Dog.prototype

const rex = new Dog("Rex");
const fido = new Dog("Fido");

console.log(rex.bark());  // "Rex says woof!"
console.log(rex.bark === fido.bark); // true — same function in memory

Diagram — What new Actually Does

Step by step

1. Create empty object.
2. Link its prototype to Dog.prototype.
3. Call Dog with this bound to that object.
4. Return the object (unless the function explicitly returns another object).

Why it matters

Forgetting new makes this point to the global object (or undefined in strict mode) — a classic silent bug.

Comparison

Own property

Set with this.x = ... inside the constructor. Exists separately on every instance.

Prototype method

Set on Fn.prototype. Exists once, shared by every instance via the chain.

Common Misconceptions

Myth"Methods should be defined inside the constructor for speed." Doing that creates a new function per instance, wasting memory. Defining on .prototype shares one function across all instances.
Myth"Calling a constructor without new just gives a warning." It silently produces wrong behavior instead of throwing — this won't be the new object at all.

Exercise

Try it — build a constructor

Every instance created by `new Car(...)` has its prototype set to Car.prototype — that's the link the chain relies on.

Key Takeaways

  • new creates an object, links its prototype, binds this, and returns it.
  • Own properties live per instance; prototype methods live once, shared.
  • Forgetting new silently breaks this binding.

Module 03 / 04

ES6 Classes, extends & super

Complete Module 2's quiz to unlock this module.

🔒 Locked — finish the Module 2 quiz above.

Explanation

class syntax, introduced in ES6, is largely sugar over the constructor-function-plus-prototype pattern from Module 2. Under the hood, a class body still produces a function whose .prototype holds the methods. What class syntax adds cleanly is extends, which wires up the prototype chain between a subclass and its parent automatically, and super, which lets a subclass call the parent's constructor or methods explicitly.

Crucially, in a derived class, this does not exist until super(...) is called — the parent constructor is responsible for creating it.

Analogy

Franchise onboarding — a new franchise (subclass) doesn't reinvent the whole business; it calls headquarters (super()) to get set up with the standard operations first, then layers on its own local specialties on top.

Example

class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound.`; }
}

class Dog extends Animal {
  constructor(name, breed) {
    super(name);       // must run before using `this`
    this.breed = breed;
  }
  speak() {
    return super.speak() + ` Specifically, a woof.`;
  }
}

const rex = new Dog("Rex", "Labrador");
console.log(rex.speak());
// "Rex makes a sound. Specifically, a woof."

Diagram — Class Chain

Comparison

Constructor function (Module 2)

You manually set Dog.prototype = Object.create(Animal.prototype) and call Animal.call(this, name).

ES6 class

extends and super() do the same two things for you, with clearer syntax and enforced call order.

Common Misconceptions

Myth"Classes in JS work exactly like classes in Java." They're still prototype-based under the hood — no real compile-time blueprint, and objects can still be reshaped at runtime.
Myth"You can use this before calling super() in a subclass." Doing so throws a ReferenceError — this isn't initialized until the parent constructor runs.

Exercise

Try it — extend a class

`instanceof` walks the prototype chain, so a Square is also an instance of Shape.

Key Takeaways

  • class is sugar over constructor functions and prototypes.
  • extends wires the prototype chain; super() must run before this is used in a subclass.
  • super.method() lets a subclass extend, not just replace, a parent's behavior.

Module 04 / 04

Advanced Patterns — Mixins, Private Fields & Composition

Complete Module 3's quiz to unlock this module.

🔒 Locked — finish the Module 3 quiz above.

Explanation

Deep inheritance chains ("God-class" hierarchies) become brittle: a change high in the chain ripples everywhere below it. Modern JS favors composition and mixins for shared behavior that doesn't cleanly fit an "is-a" relationship, alongside true encapsulation via private class fields (#field), which are enforced by the engine, not just convention.

A mixin is a function that takes a base class and returns a new class extending it with extra behavior — letting you compose independent capabilities instead of forcing everything into one linear inheritance tree.

Analogy

Lego attachments, not a family tree — instead of asking "what ancestor class already has flying?", a mixin lets you snap a Flyable module onto anything, independent of what it already inherits from.

Example — Mixins

const Swimmer = Base => class extends Base {
  swim() { return `${this.name} swims.`; }
};
const Flyer = Base => class extends Base {
  fly() { return `${this.name} flies.`; }
};

class Animal { constructor(name){ this.name = name; } }
class Duck extends Flyer(Swimmer(Animal)) {}

const d = new Duck("Duck");
console.log(d.swim(), d.fly()); // composes two independent behaviors

Example — Private Fields

class BankAccount {
  #balance = 0; // truly private, not accessible outside
  deposit(amount) { this.#balance += amount; return this.#balance; }
  get balance() { return this.#balance; }
}
const acc = new BankAccount();
acc.deposit(100);
console.log(acc.balance);   // 100
console.log(acc.#balance);  // SyntaxError — inaccessible outside the class

Comparison

Inheritance ("is-a")

Good when the relationship is genuinely hierarchical and stable, e.g. a Square is always a Shape.

Composition ("has-a" / "can-do")

Better when behavior is a capability shared across unrelated types, e.g. many unrelated classes can be Swimmer.

Common Misconceptions

Myth"Prefixing a property with underscore, like _balance, makes it private." It's still fully accessible — pure convention. Only #field syntax is enforced by the JS engine.
Myth"Deep inheritance chains are always the most reusable design." Beyond two or three levels, chains usually get harder to reason about than a flatter composition-based design.

Exercise

Try it — polymorphism in practice

Each shape calls its own overridden area() — that's polymorphism: one interface, many implementations.

Key Takeaways

  • Mixins compose independent capabilities without forcing a rigid hierarchy.
  • #field gives real, engine-enforced privacy — unlike underscore conventions.
  • Favor composition over deep inheritance when the relationship isn't a true "is-a".
  • Polymorphism lets one interface (area()) run different logic per subclass.

Summary Notes

JavaScript objects link to each other through a prototype chain that's resolved live at lookup time — never copied. Constructor functions plus .prototype were the original way to share behavior across instances; class/extends/super wrap that exact mechanism in cleaner syntax. Beyond basic hierarchies, private fields (#field) give real encapsulation, and mixins let you compose capabilities without forcing everything into one rigid "is-a" tree.
